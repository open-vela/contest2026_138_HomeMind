## 一、前因后果(为什么要做 C1,现在处于什么位置)

### 1.1 项目目标

HomeMind 是一台能感知、对话、控制家庭设备的家庭智能助手(比赛项目,OpenVela/ESP32-S3 技术栈)。总体计划把交付拆成四层:**C0(单机智能终端)→ C1(腾讯云与小程序闭环)→ R1(移动机器人)→ R2(家庭设备生态)**。C1 的验收目标是:**用户在微信小程序上登录、绑定设备、远程下发一条受控命令,命令真实执行并回显**。

### 1.2 已完成的 C0 工作(设备侧,全部有验收记录,详见 STATUS.md)

- ESP32-S3-EYE 上 OpenVela + ai_agent 稳定运行;Wi-Fi 自动联网(最强 BSSID 选择、冷启动 5/5、断网恢复 3/3);
- HTTPS/TLS 与 MiMo 大模型真实问答打通(端侧直接调 LLM);
- 配置 **Flash 持久化**(LittleFS /data 分区):断电重启后零人工配置自动恢复;
- 修复多个深层 bug:USB CDC 64 字节截断、DHCP argv、task_spawn 语义、**PSRAM 栈任务直接 flash 写导致整机冻死**(驱动保护已开启)、异步 printf 与控制台竞态;
- **本地工具**:led_control(GPIO3 板载 LED)、get_device_info(运行时长/堆/IP/固件版本)、get_button(BOOT 键),均可被 LLM 自主调用;
- **LCD 状态屏**:ST7789 240x240 显示 Wi-Fi/MiMo/LED 三个状态图标,状态变化实时联动;
- 当前固件:BIN `284121222b618718dccbde9fd76349d1f1ec50122a3744e4bc517e07f0817962`(哈希随版本推进,以 artifacts/SHA256SUMS 为准)。

### 1.3 已完成的小程序侧(Win11,contest2026_138_HomeMind/miniprogram/)

- 5 个页面骨架(index/dashboard/devices/calendar/settings)语法修复完毕(esprima 校验通过)、tabBar 图标与 sitemap 齐全、无硬编码地址,**可干净编译**;
- 页面数据均为本地 Storage 骨架,**尚无真实后端**——这正是 C1 要补的。

### 1.4 已有的历史资产

- `contest2026_138_HomeMind/server/` 是早期 FastAPI/MQTT 骨架,按总体计划 5.5 节结论:**只保留接口思路,不直接上线**,需按本文档边界重新实现;
- 腾讯云已有**域名 + SSL 证书**(用户资产);计算资源、备案、小程序 AppID 待确认(阶段一)。

### 1.5 为什么必须有 C1

设备当前只能在家庭局域网内通过串口控制。C1 让用户在公网安全地看到设备状态、下发受控命令——这是"家庭智能助手"作为产品的最小闭环,也是比赛演示的核心场景。

## 二、目标架构(总体计划已定,不可偏离)

```
微信小程序(HTTPS/WSS,只连微信后台登记的正式域名)
        │
腾讯云 Nginx(443 TLS 终结)──→ api 服务(登录/绑定/命令)──→ db(命令 ID/TTL/ACK)
        │
        └── MQTT Broker(TLS, 8883)
                ↑ 主动出站连接(家庭侧不开放任何公网入站端口)
家庭 Ubuntu 网关 gateway-agent ──本地──→ ESP32-S3 设备(已具备工具/状态上报能力)
```

**安全红线(违反即返工)**:

1. 小程序侧永不持有 AppSecret、证书私钥、设备主密钥、MiMo Token;
2. 生产环境不开"跳过域名校验";不用裸 IP/localhost/自签名证书;
3. 家庭 Ubuntu 不开 SSH/串口/裸 MQTT 到公网,只主动出站;
4. 命令必须带唯一 ID + TTL + ACK 状态(queued → acked → done / expired),云端不得把"已入队"当"已执行";
5. 高风险动作(移动、解锁、摄像/录音)必须显式确认与可撤销(本期先留接口)。

## 四、阶段二:最小云端部署(2~4 天)

验证版用**单机 Docker Compose**,不做 CLB/WAF/多实例(稳定版再评估)。

### 4.1 系统准备

```bash
# 腾讯云主机(Ubuntu 22.04/24.04)
apt update && apt install -y docker.io docker-compose-plugin
# 安全组:只放行 22(限源 IP)和 443;80 可选(仅跳转)
```

### 4.2 四个服务

| 服务 | 镜像/实现 | 职责 | 要点 |
| --- | --- | --- | --- |
| `nginx` | nginx:stable | 443 TLS 终结;`/` 反代 api;`/v1/ws` 反代 WebSocket(Upgrade 头);MQTT 8883 直通 mqtt 容器 | 证书挂载 `/etc/nginx/certs`(600 权限);HSTS 开启 |
| `api` | FastAPI(推荐,与 server/ 骨架同语言)或 Node Express | 登录、设备绑定、命令 CRUD | 无状态,连 db |
| `mqtt` | eclipse-mosquitto:2(TLS) | 设备/网关通道 | 开 8883 TLS;per-listener 密码文件;设备用 `device/<id>` 主题前缀 |
| `db` | Postgres:16(或验证版 SQLite) | users / bindings / commands | 命令表必须含 `command_id, ttl, status(queued/acked/done/expired), created_at` |

### 4.3 API 最小接口集(对齐总体计划 5.5.4)

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/v1/auth/wechat/login` | POST | body: `{code}`;服务端拿 AppID/AppSecret 调微信 `code2Session`;openid 映射 user_id;签发短期 access token + 可轮换 refresh token |
| `GET /v1/devices` | GET | 当前用户绑定的设备列表 + 最近状态 |
| `POST /v1/devices/{id}/commands` | POST | body: `{action, params}`;生成 command_id(幂等)、TTL(默认 30s);入 MQTT `device/{id}/cmd`;返回 `{command_id, status:"queued"}` |
| `GET /v1/commands/{command_id}` | GET | 查询命令真实状态(ack/done/expired) |
| `WSS /v1/ws/app` | WS | 鉴权后推送状态变化与命令 ACK;心跳;断线重连后补拉快照 |

命令动作第一版只开放白名单:`led.on / led.off / device.info`(与设备侧已验证的本地工具一一对应)。

### 4.4 验收(阶段二出口)

- `curl https://api.<域名>/v1/health` 返回 200,证书链完整(用 ssllabs 或 `openssl s_client` 检查);
- 用测试脚本模拟小程序登录 → 下发命令,db 中命令状态机正确流转;
- 未携带 token 的请求全部 401;伪造 command_id 无法越权。

## 五、阶段三:家庭网关 gateway-agent(2~3 天,Ubuntu 侧)

- 位置:家庭 Ubuntu(192.168.31.251,已有 Python 环境);**只出站连接**;
- 连接:`mqtts://api.<域名>:8883`,订阅 `device/esp32s3-eye/cmd`,发布 `device/esp32s3-eye/status` 与 `device/esp32s3-eye/ack`;
- 命令映射(第一版):收到 `led.on/off` → 通过设备串口(/dev/ttyACM0)注入 `ai_agent` 会话执行 `ask 打开灯/关灯`,或直接驱动(优先:后续让设备端新增一个云端通道命令;先用串口方案打通闭环);
- ACK 语义:设备执行完成才回 `done`;TTL 过期未执行回 `expired`;云端以 ACK 为准更新命令状态;
- 断线重连:指数退避;重连后补拉离线期间的命令查询。
