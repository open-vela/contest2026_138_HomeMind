## 2. 让小爱音箱当"说话的人"

用户要求"不要让我说话，让小爱音箱说话，麦克风接收即可"。因此把 TTS 播报
当作测试音源 —— 好处是**幅值、内容、时序都可控**，且可完全自动化。

链路（已实测）：

```
xiaoai_say.py
  → 家庭云 API  POST /v1/media/announce      （Bearer MEDIA_TOKEN）
  → MQTT        device/esp32s3-eye/speak
  → 网关        _handle_speak
  → HA          notify.xiaomi_cn_2085562629_lx06_play_text_a_5_1
  → 小爱音箱播报
```

两个可用的控制点：

- **音量**：HA service `media_player.volume_set`，实体
  `media_player.xiaomi_cn_2085562629_lx06`（初始 0.798 → 测试时拉到 `1.0`，实测生效）。
- **限流**：`/v1/media/announce` 文本 ≤300 字、`rate_limit` 6 次/分钟。

时序要点（踩过坑）：

1. 播报必须**在停网关之前**发出（MQTT→HA 要靠网关中继），发完等 4 秒再停网关独占串口。
2. 播报文本里**把目标指令重复 4 遍**（总时长约 20 秒），录音窗口排 3 个 ——
   这样不必做毫秒级对齐，任何窗口都会落在语音里。
3. **别把多条 `voice` 挤进同一个 `tr_plan` 窗口**：3 条命令排进 70 秒窗口时，
   云端只收到 1 条 POST，另两条没有产生任何请求。

## 3. 新发现：样点排布有与信号无关的刚性结构

抓回的 PCM **非零只占 49.2%**，且排布固定为 `[x, 0, x, 0]` —— 每个值重复两遍、
中间夹一个 0。**安静段也严格如此**（不是信号导致的巧合）：

```
本底段前 16 样点: -25, 0, -25, 0, 12, 0, 12, 0, 80, 0, 80, 0, 99, 0, 99, 0
最响窗口内侧样本: 300, 0, -132, 0, 0, -89, 0, -89, 0, 224, 0, 224, 0, 263, 0, 263
```

### 判据：与已知真实的 16 kHz 录音做频谱对照

对照组选 `record/pcm/*.pcm`（Sep-12 采集、已验证为**真实 16 kHz 音频**，
独立值数千、±100..11000）：

| 对象 | >4 kHz 能量 / ≤2 kHz 能量 |
|---|---|
| 对照组（真实 16 kHz 录音） | **0.02 – 0.03** |
| 设备本轮抓回的流 | **0.44** |

设备流在 **7500 Hz 处有 19.7% 的尖峰**，且高频段能量与低频段存在**镜像对应**：

- 200 / 400 / 600 / 800 Hz 内容（14.7% / 14.2% / 11.3% / 5.6%）的镜像落在 7200–7800 Hz
  → 对应那个 7500 Hz 尖峰；
- 1200 / 1600 / 2000 Hz 内容（10.2% / 4.6% / 4.2%）的镜像落在 6000–6800 Hz
  → 对应 6000 Hz 处的 4.3% 小包。

⇒ 高频段能量可**完全解释为低频内容的镜像**，因此
**真实内容带宽只有约 4 kHz —— 麦克风并非真在 16 kHz 采样**，
且每个样点被写了两遍。

`avg2`（相邻两点取平均）能消掉该伪影：镜像比从 0.44 降到 0.04–0.12。

## 4. 正确的解码方式：未定案

同一段 PCM 送本地 ASR，四种解释的对照：

| 变体 | 样点数 | 声明时长 | 镜像比 | 转写 |
|---|---|---|---|---|
| `raw @16000` | 80000 | 5.00 s | 0.46 | 这是第二点, 再回合去的灯这是第三点, 再回合... |
| `raw @8000` | 80000 | 10.00 s | 1.41 | （空） |
| `pick2 @8000` | 40000 | 5.00 s | 0.07 | （空） |
| `avg2 @8000` | 40000 | 5.00 s | **0.04** | 这是第二点,大家可以听得懂。这是第三点,大家可以... |
| `avg2 @16000` | 40000 | 2.50 s | 0.12 | **这是第二点,打开客厅的灯。这是第三点,打开客厅。** |
| `avg4 @4000` | 20000 | 5.00 s | 0.32 | 这些地址, 打开口听不懂。… |
| `avg4 @8000` | 20000 | 2.50 s | 0.67 | 这是第二遍,打开区的东西,这是第三遍… |

**两种候选各有胜负**：`avg2@8000` 时长与墙钟一致、频谱最干净，却没听出指令；
`avg2@16000` 时长只有墙钟的一半（2 倍快），反而把"打开客厅的灯"听对了。
单条样本无法区分"解码正确"与"whisper 碰巧猜中"。

**为什么不敢直接拍板**：`total_slot` 与 DMA 字宽（16 / 32 bit）无法从代码静态确定，
按不同假设推出的真实速率在 **4k / 8k / 16k** 之间摆动：

- 若 `total_slot=2`、BCLK=512 kHz、麦克风为 64×BCLK 帧 ⇒ 麦克风 fs = 8 kHz；
- 若 `total_slot=1`、BCLK=256 kHz ⇒ mic fs = 4 kHz；
- 若驱动实测投递 16000 样点/秒且这些就是有效样点 ⇒ 16 kHz。

另外做工频（50 Hz）标尺测试**不确定**：本底是宽带噪声，对照组与设备流里
都没有干净的 50 Hz 族，无法当频率基准。

### 定案方案（已备好，等板子恢复即可跑）

用**真值互不相同**的 4 条短指令各采一条，只有真正正确的解码才可能 4 条全中
（运气解释不了）：

- `_e2e_xiaoai3.sh`：对 `"打开客厅的灯"` / `"关闭卧室的灯"` / `"打开书房的空调"` /
  `"播放一首音乐"` 各做一轮"播报（重复 4 遍）→ 停网关 → 录音"，每条单独一次
  `tr_plan`（间隔 ≥15 秒）。
- `_decode_verdict.py`：对每条样本跑全部候选解码 + 声明速率，报关键词命中率与
  "全对样本数"汇总。

若仍不明确，则给驱动加一段寄存器打印（`total_slot` / `data_width` / `bclk` /
`I2S_RX_CONF1_REG` 原文），用寄存器真值定案 —— **不再用推断代替测量**。

## 5. 板子锁死：控制台零字节

第一轮 e2e 成功后，串口变成**永远读到 0 字节**。排查链（全部实测）：

| 检查 | 实测结果 | 结论 |
|---|---|---|
| `ls /dev/homemind-esp32` | → `ttyACM0` 存在 | 设备节点正常 |
| `lsusb` | `303a:1001 Espressif USB JTAG/serial debug unit` | USB 层活着 |
| `fuser -v` / `lsof /dev/ttyACM0` | 无输出（无人占用） | 不是被网关抢占 |
| `esptool -p /dev/ttyACM0 chip-id` | 连上、`Uploading/Running stub flasher` 成功、MAC `a4:cb:8f:e1:e0:08` | **芯片活着，不是硬件损坏** |
| `scripts/build.sh flash` | 写入 1422632 字节、`Hash of data verified.`、rc=0 | flash 通路正常 |
| 复位后裸读控制台 | **0 字节** | 应用层没有起来 |
| `dmesg`（复位前后） | **无任何 USB 重枚举** | 复位没有真正生效 |

已尝试且**全部无效**的软恢复：RTS/DTR 四种时序组合、标准 EN 复位脉冲、
`usb unbind/rebind`、esptool `--after hard_reset`、**重新刷写固件**。

⇒ 芯片被闩住（很可能停在 ROM 下载模式），**只有物理断电（拔插 USB）能恢复**。
这与既有铁律"RTS 软复位替代不了真下电、`uhubctl` 在本机不可用"一致。

顺带确认一条操作事实：**pyserial 打开端口时默认会 assert DTR/RTS**，而 ESP32-S3 的
USB-Serial-JTAG 把它们桥到芯片的 EN/BOOT 脚 —— 同一时刻 `rts=True` 读到 **0 字节**，
`rts=False` 立刻出 `nsh>` / `vela>`。`tr_plan.py` 已在 `open()` 之后显式放开两线。
