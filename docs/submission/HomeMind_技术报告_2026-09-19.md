## 2. 摘要

HomeMind 以 ESP32-S3-EYE 为端侧载体，运行 openvela 与 `ai_agent`，构建「端侧感知执行—家庭私有云编排—真实家电回读」三层家庭中枢；语音入口复用家人已在用的小爱音箱，敏感音视频不出家庭网。

实测：说「你好，openvela，打开多功能房灯光」→ 吸顶灯真亮、板载 LED 同步、自动生成待办、小爱播报确认；仅说唤醒词则不执行。关灯由 HA 真实状态触发睡前模式，生成两条待办并播报晚安。

创新点：端侧工具白名单 + 家庭侧风险词 fail-closed 双层护栏、跨设备状态回读强制确认、自然语言触发的运行时 Skill。端侧指定词 KWS 尚未达标，如实披露。

## 3. 正文

### 3.1 绪论

#### 3.1.1 项目背景与问题定义

智能家居的入口正在碎片化。一个普通三口之家，灯在米家、空调在另一个 App、音箱是第三个入口；老人和儿童记不住 App 路径，最后所有设备都退化成「墙上开关」。与此同时，把摄像头与麦克风常连公有云，让不少家庭在隐私上难以接受。

HomeMind 面向的是**有老人与儿童、已有一部分米家/HA 设备、对隐私敏感**的城镇家庭（25–45 岁为主力购买者，实际使用者常为长辈）。要解决的具体问题有三个：

1. **门槛问题**：零学习成本的家庭语音入口，不要求家人装新 App、换新设备；
2. **真实性问题**：语音助手「答应了」不等于灯真的亮了——控制结果必须回读真实设备状态；
3. **隐私问题**：语音与视觉数据默认留在家庭局域网内，仅在必要且用户允许时才出网。

#### 3.1.2 关键技术难点

- **端侧资源受限下的 Agent 运行**：在 MCU 级的 ESP32-S3（8 MB PSRAM / 16 MB Flash）上运行 openvela 与官方 `ai_agent`，同时要挤出 I2S 音频、LCD 图形与摄像头的能力预算，栈与 DRAM 都极紧张。
- **端到端时延与串口瓶颈**：板子与家庭网关之间只有一条串口，网关既要维持两条 MQTT 连接，又要在串口上做「自然语言 → 设备动作 → 文本回读」的往返，任何一个环节阻塞都会让整条链路假死。
- **跨系统状态一致性**：米家 → Home Assistant → HomeMind → 网关 → 板子，四跳链路中任何一跳的 `unavailable` 都会让云端「看不见设备」。
- **唤醒策略的算力/准确率矛盾**：端侧指定词唤醒（KWS）在低算力下难以同时满足低误报与低漏报，本项目最终选择「端侧能量触发 + 家庭私有云文本校验」的分工。

#### 3.1.3 创新点

- **交互层**：不新增硬件入口，复用家人已在使用的音箱作为中文语音入口，配合板载 LED 与播报形成"看得见、听得到"的双反馈。
- **技术层**：端侧工具白名单与家庭侧 `RISK_KEYWORDS` fail-closed 两层护栏，保证 LLM 的规划结果只能落在被允许的真实动作上；任何设备控制都强制回读 HA 真实状态后才判定 `done`。
- **场景层**：把「睡前」这样的家庭仪式固化为可被自然语言触发的运行时 Skill，由真实灯状态变化自动激活，无需用户显式命令。

#### 3.2.2 方案论证与选型

**开发板选型**：ESP32-S3-EYE 自带麦克风阵列、摄像头与 LCD，且官方 openvela 仓库已提供 `ai_agent` 与完整 BSP（`esp32s3-eye`）。选它的核心理由是「AI 能力落地成本最低」——不需要自己从零写音频与显示驱动，能把时间花在协同逻辑上。同价位竞品（纯 Wi-Fi MCU 板）缺少摄像头与显示，难以在本届「图形/AI/多媒体至少落地一项」的要求上体现完整度。

**端云职责划分**：

| 职责 | 端侧（板子） | 家庭私有云 | 公有云（腾讯云 · hfy-ai.cloud） |
| --- | --- | --- | --- |
| 采集 | I2S 音频、摄像头 | — | 媒体帧 / 音频上报接口（`/v1/media/frame|audio`，默认不外发） |
| 唤醒 | 能量触发（离线可用） | **唤醒词文本校验与剥离** | — |
| 语义 | 本地规则快路径 | 本地 LLM（首选） | MiMo（可关闭） |
| 执行 | LED / 设备信息 | 待办、播报、编排 | 设备指令下发与回执（`/v1/devices/{id}/commands`、`/v1/commands/{id}`） |
| 状态 | 上报自身能力 | SQLite 落库、HA 回读 | 设备绑定关系与在线状态；Web 端可观测 |
| 账户与入口 | — | — | 微信登录（`/v1/auth/wechat/login`）· Web 官网与运维控制台 · Swagger 接口文档 |

**断网/弱网降级**：家庭局域网内网中断时，板载 LED 与本地规则仍可用；若外网中断，本地 LLM 与本地 ASR 仍可完成理解与播报，仅米家云端控制失效（此时降级为「记录待办 + 提示用户」）。隐私模式 `PRIVACY_MODE=1` 打开时，模型调用与存储均留在家庭内。

**与备选方案对比**：

| 方案 | 优势 | 为何未选 |
| --- | --- | --- |
| 全云端语音助手直连家电 | 实现最简单 | 需要音视频出网，隐私不达标；也无法做板载 LED 等本地反馈 |
| 端侧独立完成全部 ASR+LLM | 完全离线 | ESP32-S3 算力与内存无法承载可用精度的中文 ASR + LLM |
| **端侧感知 + 家庭私有云理解（本项目）** | 隐私可控、真实设备闭环、可断网降级 | 需要家庭侧常开一台小型服务器 |

#### 3.2.3 关键模块设计

- **端侧 `ai_agent`**：openvela 官方 Agent 框架，提供工具注册表、Skill 加载器与串口 CLI。本项目在其上注册了 LED 控制、设备信息等白名单工具，并以 `ask <自然语言>` 作为网关的调用面。
- **家庭网关**：只主动出站，同时维护「云 MQTT」与「本地 MQTT」两条连接；收到命令后立刻回 `acked`，把串口执行放到独立线程，避免阻塞 MQTT 网络循环导致 keepalive 饿死。
- **家庭 API**：FastAPI + SQLite，负责鉴权（JWT / `MEDIA_TOKEN`）、命令 TTL 与防重放、HA 适配与实体白名单、待办与会话管理。
- **HA 桥**：把设备抽象成可观察实体，所有控制动作执行后强制回读，`unavailable` 视为失败并如实上报。
- **公有云 API（HomeMind C1）**：FastAPI 实现，提供微信登录、设备绑定/解绑、指令下发与回执查询、媒体帧与音频上报、播报下发、WSS 实时通道；由 nginx 统一终止 TLS（TLS 1.2/1.3 + HSTS），官网静态资源与 API 同域，避免跨域与证书分治。
- **Web 端**：以原生 HTML / CSS / JavaScript 实现，无框架、无构建步骤——包含品牌官网（5 个滚动板块）、「栖心 · 运维控制台」（登录视图 + 服务状态 / 数据存储 / 接入设备三张状态卡）与 FastAPI 自动生成的 Swagger 接口文档（`/docs`）。选择原生实现的原因是：家庭场景的云端演示机配置有限，静态文件直接由 nginx 托管可省去 Node 构建链，也便于长期免维护运行。

### 3.3 核心算法与技术原理

#### 3.3.1 AI 算法实现

**云端模型（大赛 MiMo）**：模型 `mimo-v2.5`，接口 `https://api.xiaomimimo.com/v1/chat/completions`（HTTPS 443），鉴权为 Bearer Token。它承担两类任务：复杂指令的语义规划，以及把用户口语规范化为可执行的动作序列。System Prompt 中明确列出可用动作白名单与输出 JSON Schema。

**端侧/家庭侧模型**：
- **本地 LLM**：`qwen2.5-1.5b-q4km`（llama-cpp-python，Q4_K_M 量化），家庭侧 CPU 推理，首字约 10.7 s。它是默认的规划器——**只在本地模型失败或用户显式允许时才升级到 MiMo**。
- **本地 ASR**：`faster-whisper small`（int8 量化），单句约 2.0 s，静音门限 `ASR_MIN_RMS` 可配（当前 50）。
- **端侧视觉**：实验性的混合存在检测（肤色 + 边缘 + 运动 + TFLM 分数融合），**不是**通用人体识别，仅用于演示端侧多媒体链路。

**算力占用**：端侧常驻内存中，`ai_agent` 主任务栈 32 KB，音频采集线程 32 KB；摄像头/TFLM 路径按需分配，不长期占用 DRAM。

#### 3.3.2 关键机制设计

**双层护栏（fail-closed）**：

1. 端侧工具白名单：`ai_agent` 只暴露 `led_control`、设备信息等有限工具，未注册的能力无法被自然语言触发。
2. 家庭侧 `sanitize_plan()`：对 LLM 输出做 `RISK_KEYWORDS` 检查与**占位符检测**（拦截模型照抄 prompt 中的示例），任一项命中即拒绝整份计划，绝不降级执行。

**最小任务保证**：即使语义层只识别出「有动作但无法归类」，`ensure_min_task()` 也会补出唯一一条确认待办——保证用户每次说话都留下可追溯的记录，而不是「助手答应了但什么都没发生」。

**场景预算回落**：LLM 若给出与文本不符的判断（例如把普通指令误判为睡前场景），`reconcile_plan()` 会回落到确定性规则，防止误触发整场景。

**强制状态回读**：任何设备控制完成后，都向 Home Assistant 查询该实体真实状态；与期望不一致即判失败并上报 `expired`。

#### 3.3.3 openvela 系统能力的深度运用

本项目**三项核心能力均有落地**：

| openvela 能力 | 落地内容 | 用到的组件 |
| --- | --- | --- |
| **AI** | 官方 `ai_agent`：工具注册表、自然语言任务规划、运行时 Skill 加载器（扫描 `skills/` 下的平铺 `.md`） | `packages/ai_agent`、NuttX 任务/信号量/TLS |
| **多媒体** | I2S 麦克风连续 PCM 采集与上传；摄像头图像通路；两路 DMA 音频缓冲 | NuttX `audio` 上层框架、`esp32s3_i2s` 驱动、`nuttx/drivers/audio/audio_i2s.c` |
| **图形** | LCD 状态仪表盘（240×240，RGB565 直写 framebuffer）：联网/助手状态、mood 表情，以及**与控灯工具共用 `/dev/gpio0`（GPIO3）的「灯」状态芯片** | NuttX framebuffer (`/dev/fb0`)、`nuttx/ioexpander/gpio` |

其中「图形」一项的可见性是端到端可验证的：真实灯状态变化触发自动场景后，网关向设备下发 `led.off` / `led.on`（`commands.status = done`），板载 LED 实际翻转；LCD 的「灯」芯片读取的是**同一个 GPIO**，因此**家人对小爱说「关灯/开灯」所引发的灯光动作，会实时体现在板子屏幕上**，无需为屏幕单独新增硬件或链路。

**对 openvela 的优化与改进建议**：

1. **补全音频 ioctl 契约**：在排查「端侧监听循环不触发」时发现，调用侧 `open` + `AUDIOIOC_CONFIGURE` 后若缺少 `AUDIOIOC_GETBUFFERINFO`，`audio_allocbuffer()` 会因为 `nbuffers` 从未赋值而立即失败，且 **errno 保持 0**，导致极难定位。建议在 `audio.c::audio_allocbuffer()` 失败路径上写入明确的 errno（如 `EINVAL`），或在 `CONFIGURE` 内自动补齐 `nbuffers` 默认值。
2. **I2S 驱动的 RX 帧宽处理差异**：ESP-IDF 在 ISR 内按 `bits_per_sample` 拆分 32 位 FIFO 字，而 NuttX 侧不拆。实测容器产出率与 `[I2SCLK]` 声明的声学采样率存在约 4× 亏空（寄存器级对账全部一致）。建议在上游驱动中补齐该拆分逻辑，或在文档中明确该差异，避免后续开发者重复排查。
3. **烧录布局文档化**：本项目的构建产物无独立 IDF bootloader、无分区表，整镜像须写在 `0x0`。建议在 openvela 的 ESP32-S3 移植文档中显式说明该布局，避免误写 `0x10000` 造成启动环。

### 3.4 系统实现

#### 3.4.1 软件/固件架构

固件以 **overlay 作为唯一真相源**：`firmware/ai_agent_overlay/` 下的源文件由 `scripts/build.sh deploy` 逐文件覆盖到 `$OPENVELA_ROOT/packages/ai_agent/`，再由 `scripts/build.sh build` 编译出 `artifacts/nuttx.bin`。所有对 openvela 的改动都以「带标记的幂等补丁」形式落在部署脚本中（如 `HM_FIX_LISTEN24_BUFINFO`、`HM_I2S_RX_DIAG`），保证重放可复现。

仓库代码规模（按提交分支 HEAD 实测）：Python 63 个文件 / 7 446 行；C 20 个文件 / 17 789 行；Web 前端 2 个文件 / 1 229 行（`web/landing/`）；Markdown 114 个文件。

#### 3.4.2 数据流与关键流程

**流程一：语音指令闭环**

```text
用户「你好，openvela，打开多功能房灯光」
        │
        ▼
[采集] 小爱音箱 / 板载麦 → 家庭私有云 /v1/voice/command
        │
        ▼
[唤醒] _wake_hit() 校验唤醒词 → strip_wake_word() 剥离
        │
        ▼
[理解] local_rules 快路径 → 未命中则本地 LLM → 必要时 MiMo
        │
        ▼
[护栏] sanitize_plan() 风险词 + 占位符检查（fail-closed）
        │
        ▼
[执行] ① 米家控灯（经 HA）  ② led.on（经网关串口）  ③ 创建待办  ④ 播报
        │
        ▼
[回读] 查询 HA 真实状态 → 一致才置 done → 写 SQLite
```

**流程二：场景自动触发（睡前）**

```text
HA 观察到 light.* 由 on → off
        │
        ▼
ha_bridge: entity_id == HA_BEDTIME_LIGHT ? → 冷却期内去重（180 s）
        │
        ▼
场景编排：批量创建待办（睡前刷牙 / 检查门窗与闹钟）
        │
        ▼
外围动作：led.off（串口→板子）+ 播报「好的，进入睡前模式。待办已记下，晚安。」
```

**流程三：板载执行（网关串口）**

```text
云/本地命令 → 网关 subscribe device/esp32s3-eye/cmd → 立即回 acked
        │
        ▼（独立线程，避免阻塞 MQTT loop）
串口 write "ask 打开灯\n" → 板端 ai_agent 自然语言规划
        │
        ▼
板端回 [Agent]: {"led":"on"} → 网关校验 JSON 中的 led 字段
        │
        ▼
一致 → command done；不一致/超时 → expired
```

**AI 工具对开发效率的提升**：本项目在约 7 周内由单人完成从 openvela 固件适配、家庭私有云、网关到语音链路的全栈实现，其中最能体现 AI 提效的是**底层驱动的取证型调试**——面对「串口疯狂刷屏但不触发」这类缺乏日志的现象，AI 协作完成了「源码对照找出 7 处 `AUDIOIOC_CONFIGURE` 中唯一漏掉 `GETBUFFERINFO` 的那一处」这种需要跨文件比对的定位工作。

**遇到的问题与解决方式**（择要）：

1. **端侧监听循环恒不触发**：表现为串口 197 行/s 刷屏、CLI 被饿死。通过跨文件比对 7 处缓冲配置调用点，定位到监听循环缺少 `GETBUFFERINFO`，导致 `nbuffers` 从未赋值、分配立即失败且 errno 为 0。补丁后刷屏归零。
2. **软复位无法启动板子**：曾误判「只有物理拔插能恢复」。通过复位方式 A/B 标定，明确该芯片 `hard_reset` 只是 RTS 脉冲（无效），必须用 `watchdog_reset`；并确立「esptool 返回码 0 不能证明芯片活着，必须看实测字节数」的判据。
3. **双实例导致录音永久阻塞**：固件会在启动后自动拉起 Agent，若在 `nsh>` 提示符出现后手动再启动一次，会双开音频设备。确立了「两个实例计数都必须恰好为 1」的验收判据。

### 3.7 总结与展望

#### 3.7.1 成果总结

HomeMind 交付了一条**可复现、可被评委独立验证**的家庭 AI 中枢链路：端侧 openvela 固件（含音频与显示能力落地）+ 家庭私有云（本地 LLM/ASR、SQLite、场景编排）+ 网关（双 MQTT、串口执行）+ HA 真实设备闭环。语音入口不需要新硬件，控制结果以真实设备状态为准，隐私数据默认留在家庭内。全部代码、AI 日志与证据文档均在赛事分配的专属仓内。

#### 3.7.2 应用前景与商业价值

**目标受众**：25–45 岁的城镇家庭购买者，实际使用者常为家中长辈与儿童；核心场景是「一句话完成睡前/到家/离家」这类高频、固定、跨设备的家庭仪式。地域上优先面向已有米家生态、且家里已有一台常开电脑/NAS 的家庭。

**商业模式**：采用「软件订阅 + 硬件可选」的双轨结构。家庭私有云软件按年订阅（含模型更新、场景库、多设备扩展）；硬件侧不强制自研整机，而是先以「适配清单」形式支持已售出的开发板与小型主机，降低用户的初始迁移成本。规模化潜力来自两点：一是**不需要用户更换任何家电**，二是**不需要用户把数据交给第三方**——这两点恰好是当前智能家居渗透率的两大阻力。

**可扩展方向**：把运行时 Skill 开放给家庭自行编写（如「老人吃药提醒」），形成家庭自有的场景库；以及把同一套端云协同框架平移到车载与养老场景。

#### 3.7.3 不足与未来工作

如实列出当前缺口，均为后续工作项：

1. **端侧指定词 KWS 未达可用**：端上逻辑回归模型在实机上得分恒为 0，根因是训练域与实机域的特征偏移（训练样本的过零率均值 ≈0.12，实机 ≈0.48）。当前唤醒词校验在家庭私有云以文本方式完成；端侧高准确率唤醒仍需重采真实人声样本重训。
2. **板端 24/7 常驻监听未闭环**：缓冲分配缺陷已修复（刷屏归零），但随后阻塞在采音启动路径，控制台失聪。需要继续定位 I2S 驱动的缓冲信号量等待点。
3. **SD 卡持久化未生效**：板端一直报 `/sd -> /data (no SD)`，配置双写（`/sd/agent` + `/data/agent`）尚未真正落地。当前 `/data` 分区位于镜像区之外，可承受重新刷写，但掉电仍有风险。
4. **I2S 采样率约 4× 亏空未定案**：寄存器级对账一致但容器产出率对不上，需在驱动层补齐 32 位 FIFO 字按位宽拆分逻辑。
5. **端侧视觉为实验性存在检测**，非通用人体/身份/手势识别，不作为产品能力宣称。
