# HomeMind 大赛技术进度报告

> 报告日期：2026-08-07  
> 项目：`contest2026_138_HomeMind`  
> 赛道：AI 硬件产品创新  
> 目标硬件：ESP32-S3-EYE  
> 核心软件：OpenVela / Apache NuttX / `ai_agent`  
> 当前主线：ESP32-S3-EYE 独立连接家庭 Wi-Fi，直接通过 HTTPS 调用 MiMo，不依赖 Windows/Linux 网关、MQTT Broker 或代理。

## 1. 结论摘要

HomeMind 已完成 OpenVela/`ai_agent` 的基础上板和一版带 HomeMind 网络诊断、Wi-Fi 状态机及 TLS 修改的固件构建。现有固件文件可校验，历史记录表明开发板能够启动到 `nsh>`，执行 `ai_agent` 后进入 `vela>`。ELF 字符串也证明 `[HM-WIFI]`、`[HM-NET]`、`[HM-TLS]`、`[HM-LLM]` 等修改已经进入 7 月 27 日的固件，而不只是停留在源码文件中。

但当前尚未形成大赛可演示的核心闭环。已记录的 5 次无代理 `net_test` 均在 TLS 层失败；真实 MiMo 问答、掉电持久化和 LLM 控制 LED 均没有通过验收。现阶段可以演示“固件启动和进入 `vela>`”，不能诚实地演示“自动联网 → 直连 MiMo → 安全工具调用 → 掉电后仍可用”的完整产品链路。

当前最关键的技术阻塞是：

1. TLS socket 超时返回 `errno 11` 时，代码仍使用 `mbedtls_net_recv`，没有把 `EAGAIN/EWOULDBLOCK` 转换为 `MBEDTLS_ERR_SSL_WANT_READ`；这与既有 `-0x004c` 失败现象一致。
2. Wi-Fi 日志函数会输出完整 `wapi psk ...` 命令，实际运行时会泄露 Wi-Fi 密码，必须先修复再采集或提交日志。
3. 当前 `/data` 仍是 TMPFS；配置保存接口即使返回成功，断电后仍会丢失。
4. HomeMind 三个本地工具只有独立 C 草案，没有被部署脚本复制、没有注册进 `ai_agent`，也没有进入现有 ELF。
5. 当前目录不是有效 Git 仓库，无法证明固件对应的源码提交，也不满足可靠版本追踪和比赛交付要求。

## 3. 当前系统架构与范围

当前有效主线应统一为：

```text
用户串口输入
  → ESP32-S3-EYE
  → OpenVela / NuttX 网络栈
  → ai_agent
  → Wi-Fi / DNS / TCP / TLS 1.2+
  → MiMo Token Plan HTTPS 接口
  → 白名单本地工具（device_status / light_set / scene_set）
  → 板载 LED 或后续确认的 GPIO/UART 设备
```

以下内容属于早期“端云协同”方案，与当前独立版目标冲突，应冻结为历史支线，不再作为 P0：

- Windows FastAPI 中转服务；
- MQTT Broker、Mosquitto 和 Windows 模拟灯具；
- 微信小程序；
- Linux 网关、Clash 或其它 HTTP/SOCKS 代理；
- STM32F103、视觉、语音、MCP、Web 搜索等增强项。

工程内 `PROJECT_GUIDE.md`、`default_config.json`、`server/`、`miniprogram/` 和部分旧文档仍描述 FastAPI/MQTT/小程序架构，需要在主线打通后统一归档或重写，避免评委误判最终产品形态。

### 4.2 Phase A：基线与诊断日志

状态：**已进入固件、未完成验收**。

已具备：

- Wi-Fi、网络、TLS、LLM 固定日志前缀已进入 ELF；
- TLS 代码记录直连/代理路径、TCP 结果、SNI、TLS 版本范围、握手错误和 HTTP 状态；
- 代理默认未配置时走直连，并输出 `No proxy configured — using DIRECT connection`。

未满足或存在问题：

- `wifi_run_cmd()` 会输出完整命令；调用 `wapi psk` 时会把密码写入串口日志，违反敏感信息要求；
- HTTPS 路径通过 `mbedtls_net_connect()` 隐式解析域名，没有输出 DNS 解析所得 IP；现有显式 DNS 日志位于 plain HTTP 路径，不能证明 TLS 路径的 DNS 阶段；
- 没有输出网关和 DNS 服务器配置；
- WPA2 阶段只记录 shell 命令返回码，没有真实的认证/关联事件证据；
- 仓内没有不含敏感信息的真实串口验收日志。

### 4.3 Phase B：自动 Wi-Fi

状态：**状态机已进入固件、未实机验收**。

已具备：

- `IDLE / CONNECTING / ASSOCIATED / DHCP / READY / RETRY_WAIT / FAILED` 状态机；
- `wapi psk <iface> <pass> 3 2` WPA2 参数；
- 通过真实 IPv4 地址判断网络可用；
- 5、10、20、40、60 秒递增退避及断线检测；
- 从 `agent_config` 读取凭据的 `wifi_reconnect` 路径。

主要缺口：

- 单次关联等待 5 秒、DHCP 等待 15 秒，总计约 20 秒，低于需求中“不低于 30 秒”的建议；
- `ifup`、`wapi mode`、`wapi psk`、`wapi essid` 的错误码只记录、不阻断状态转换；
- `ASSOCIATED` 状态是固定等待后的命名，并未证明真实完成 WPA2 关联；
- 配置写入当前 TMPFS，不能满足重启/断电自动恢复；
- 未见路由器断开/恢复后的实机重连记录；
- 日志密码泄露问题使当前版本不适合直接做验收记录。

### 4.4 Phase C：无代理 HTTPS/TLS

状态：**当前 P0 阻塞**。

已知事实：

- 迁移记录写明，现有固件成功烧录并进入 `vela>`，但 5 次无代理 `net_test` 均在 TLS 层返回 `0x1`；
- 早期详细现象为 TLS `-0x004c`、socket `errno 11`；
- 当前代码把 socket 设为 blocking，并配置 `SO_RCVTIMEO`，随后把 `mbedtls_net_recv` 直接注册为 BIO；
- `mbedtls_net_recv` 在 NuttX 返回 `EAGAIN/EWOULDBLOCK` 时不会自动变成 `MBEDTLS_ERR_SSL_WANT_READ`，握手循环因而仍可能把临时不可读当作永久失败；
- 已设置 30 秒整体握手截止时间和 SNI，TLS 1.2 保留；
- 证书模式为 `MBEDTLS_SSL_VERIFY_OPTIONAL`，且没有 CA bundle，当前不能宣称服务端身份校验安全通过。

当前最可能的首个修复点是实现 ai_agent 自有 socket BIO：对 `EAGAIN`、`EWOULDBLOCK` 和可恢复的 `EINTR` 返回 `MBEDTLS_ERR_SSL_WANT_READ`，保留总体握手截止时间，并对其它错误返回永久失败。修复后必须连续直连测试至少 5 次，并补充 DNS、TCP、TLS、HTTP 分层日志。

### 4.5 Phase D：MiMo 直连文本问答

状态：**未验收，受 Phase C 阻塞**。

当前固件包含 MiMo 相关字符串和 `mimo-v2-flash`、`mimo-v2-omni` 模型名，但没有真实 `ask` 成功记录。工程资料存在三套不一致信息：

- ELF 中出现主机 `api.xiaomimimo.com`；
- `tools/test-llm.md` 写 `token-plan-cn.xiaomimimo.com/v1`；
- 旧 FastAPI 代码写 `https://api.mimo.xiaomi.com/v1`，模型为 `mimo-v2.5`。

CLI 文档也同时出现 `set_llm <host> <model> [api_key]`、`set_llm mimo <key>`、`router_set`/`router_model` 三种流程。必须以当前比赛分支实际 CLI 和 MiMo Token Plan 官方接口为准，统一端点、模型和操作手册，再做一次真实非流式问答。API Key 只能由操作者在设备端输入，报告和日志不得保存 Key。

### 4.6 Phase E：Flash 持久化与日志

状态：**仅设计文档和 overlay 草案**。

四份保存的 ESP32-S3-EYE 配置证据中只有 `CONFIG_FS_TMPFS=y`，没有 LittleFS/SPIFFS/SMARTFS 持久文件系统配置。ELF 中也没有检出 LittleFS、SPIFFS、SMARTFS 或 NXFFS 字符串。因此：

- 当前 `/data` 掉电丢失；
- Wi-Fi/LLM 配置的“保存成功”不等于掉电保存成功；
- `log_show`、`log_clear` 不在现有 ELF 中；
- 分区表、挂载点、磨损控制、日志轮转和异常恢复都未验收；
- `persistent-storage-guide.md` 中的分区地址仍是建议值，不能直接用于实机，必须先核对实际 Flash 容量、现有镜像布局和 OpenVela 板级支持。

### 4.7 Phase F：HomeMind 最小工具闭环

状态：**源码草案，未集成**。

`tools/staging-homemind_tools.c` 实现了 `device_status`、`light_set`、`scene_set` 的函数草案，但：

- `deploy-to-vm.sh` 和 `scripts/build.sh` 只部署三个 infra 文件，不部署 `staging-homemind_tools.c`；
- 文件中只有工具注册示例注释，没有实际注册函数调用；
- 现有 ELF 中没有 `tool_device_status`、`tool_light_set`、`tool_scene_set`；
- 系统提示词尚未接入实际 `SOUL.md`；
- 默认 LED GPIO 2 和 2/4/5/12/13/14/15/16/17/18 白名单没有板级验证，可能与摄像头或其它外设引脚冲突；
- `scene_set` 忽略 GPIO 命令返回值，却固定返回 `success: true`；
- 工具通过 `system("gpio ...")` 执行，虽然参数有白名单，但仍需确认目标固件是否包含兼容的 `gpio` 命令，并优先评估直接驱动 API。

因此当前不能宣称已实现 `ask 打开灯`。

## 5. 非主线模块现状

这些模块不应阻塞纯 ESP32 MVP，但在仓库中会影响评审观感，应明确标为历史/冻结：

### FastAPI

- Python 源码语法可解析；
- 当前环境没有安装服务端依赖；
- `main.py` 引用不存在的 `services.ai_service`、`device_service`、`calendar_service`；
- 路由使用各自内存字典，未接入 SQLite/MQTT；
- `docker-compose.yml` 引用缺失的 Dockerfile、Mosquitto 配置和 Nginx 配置；
- 没有自动测试。

结论：仅是接口骨架，不能运行，也不属于当前主线。

### 微信小程序

- `app.js` 通过 JavaScript 语法检查；
- 5 个页面脚本全部存在语法错误；
- 10 个 tabBar 图标和 `sitemap.json` 缺失；
- 多个 URL 模板、动态字段名和版本字符串损坏；
- 仍依赖硬编码 `192.168.1.100`、本地存储和不存在的 API。

结论：当前不能在微信开发者工具编译；建议冻结，不投入 P0 工时。

### 样例 app / quickapp / board

- manifest 映射路径使用队伍编号 138；

结论：官方 manifest 同步后不会自动得到一个名为 HomeMind 的可构建应用；当前核心修改依靠脚本覆盖 `packages/ai_agent`。
